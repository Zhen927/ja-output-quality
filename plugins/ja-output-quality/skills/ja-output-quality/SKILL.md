# ja-output-quality — 日本語出力の不変則と独立レビュー

体裁（段落か箇条書きか、敬体か常体か、番号の振り方）は体裁スキルが決める。本スキルはそこに触れず、どの体裁でも成り立たなければならない不変則だけを扱う：**真実性・校准（主張の強さ＝証拠の強さ）・読者コスト・母語性・語域**。既存スキルとの分担は、natural-japanese が文書型と表現、japanese-tech-writing が論証、customer-qa-style が顧客回答の体裁。本スキルはその下に敷く共通層と、書き手から切り離したレビューを担う。

## 0. 原理（なぜ規則を増やしても直らないか）

1. 過度防御・過度説明・工程の自己言及・均質な構造・英語型の統語は、知識不足ではなく生成時の既定傾向である。参照資料を増やしても再発する。
2. 書いた本人（同じコンテキスト）は自分の文を審査できない。直前に生成した文を「所与」として弁護する。審査は別コンテキストで、書き直し権限なしで行う。
3. 規則は増やすほど守られなくなる。生成時に持たせる規則は10条以内に圧縮し、残りは機械検出と参照ファイルに逃がす。良い実例1本は禁止語50個より強い。
4. 機械検出は疲れも忖度もしないが、表層しか見えない。判断は別コンテキストのレビュアーが行い、最終決定は親が行う。
5. 過度防御と証拠越境は同じ欠陥である。主張の強さが証拠の強さから外れているだけで、弱すぎるか強すぎるかの違いしかない。どちらも「結果＋境界＋未検証範囲」という一つの操作で直る。

## 1. 生成時の制約 — 出力憲法10条

書き始める前に読む。体裁は規定しない。

1. **結論が最初の一文。** 前置き・予告・謝辞は正文に入れない。
2. **主張の強さ＝証拠の強さ。** 「かもしれない」「と思われる」「かと存じます」は、具体的な不確実性の源が指せるときだけ書く。「確実に」「十分に」「必ず」「問題ありません」は、指せる証拠があるときだけ書く。どちらも指せないなら「結果＋境界＋未検証範囲」の形に書き換える。前提・適用範囲・未検証項目は削らない（形だけ変えてよい）。
3. **対象だけを書き、工程を書かない。** 「確認済み」「検証済み」「多角的に検証した」「AIとして」「私は〜を確認した」のような生産過程の文は正文に入れない。正文に入れてよいのは「何が保証されているか（仕様・規約・定理）」「何が観察されたか（実測・検証・一次情報）」「境界はどこか」の3種だけ。
4. **一文一役。** 各文は主張・証拠・境界・接続のどれか一つを担う。削っても失われるものがない文は存在させない。背景は繰り返さず、手順は再生せず、パラメータは積まない。読者が欲しいのは結果のインターフェースであって工程の再放送ではない。
5. **事実・推論・転述・推測を分け、互いに偽装しない。** 事実には出典、推論には前提、転述には出所、推測には【要確認】【推定】の標識。
6. **数値は条件と幅を伴う。**「元データがCSVなら20〜30%」「同時実行10以下の前提で」。裸の数値は書かない。
7. **母語の統語で書く。** 主語を省く。無生物主語＋他動詞、「〜することができる」「〜において」「〜という観点から」「〜を行う」の名詞化を避ける。目録は `references/ja-surface.md`。
8. **均質な構造を作らない。** 段落の長さ・節の厚み・書き出しの型を揃えない。重要な箇所は厚く、軽い箇所は薄く。同じ鋳型を3回続けない。内容が要求しないのに「大きく分けて3つ」にしない。
9. **強調は内容で行い、装飾で行わない。** 太字は段落に核1箇所まで。絵文字は導航ラベル以外に使わない。「非常に」「極めて」「圧倒的」は削る。感嘆符は使わない。
10. **語域は読者との関係に従う。** 顧客向けは敬語規範（二重敬語禁止、「させていただく」は許可・恩恵の場面だけ、「〜になります」「〜のほう」禁止、クッション言葉は一通に1回）。文書では「貴社」、会話では「御社」。全角英数・半角句読点・簡体字の混入なし。

**優先順位**：体裁スキルの体裁規定 ＞ 本スキルの体裁上の助言。本スキルの2・3・5条（校准・工程排除・四分法）＞ どのスキルの表現上の好みよりも優先。衝突したら「読み手の得になるほう」を選ぶ。

## 2. 独立レビュー — 書き手と審査を分ける

完成した文章に対して、別コンテキスト（サブエージェント）でレビューを行う。詳細なプロンプトと出力形式は `references/review-protocol.md`。要点は次の通り。

**Lane 0 機械検出（決定的）**
- 主：natural-japanese の `scripts/lint.py --json`（uv 環境。常套句・翻訳調・体言止め率・段落構造・語彙多様性）。
- 補：本スキルの `scripts/ja_lint.py --json <file>`（標準ライブラリのみ。敬語・工程叙述・語尾の確信度均し・制約のない「できる」・幅のない数値・未確認事項の標識・字形）。uv が使えない環境ではこちらだけで回す。
- findings は疑いの提示であって指示ではない。すべて台帳に載せ、直す/残す（理由）を判断する。

**Lane A 存在性（表現）** 一文ごとに機能（主張/証拠/境界/接続/工程/装飾/反復）を付け、過度防御・審査式話語・過度説明・装飾・鋳型反復を判定する。
**Lane B 成立性（内容）** 主張文だけを抜き出し、種類（仕様保証/実測観察/文献転述/推測）、証拠が本文または引用範囲にあるか、外挿していないか、強い語・弱い語に対応する証拠があるかを判定する。
**Lane C 表層と語域** 翻訳調、敬語、字形・記号を判定する。

**レビュアーの禁止事項**：書き直さない、弁護しない、褒めない、原文を要約しない。出力は「原句 / 類型 / 判定 DELETE・REWRITE・HOLD / 修正指令（何を補うか。文案は書かない）」の行だけ。末尾に各 Lane の PASS/WARN/FAIL。

**親（書き手）の仕事**：3 Lane の所見と Lane 0 の findings を一つの判断台帳に統合し、finding ごとに「直した」か「残す（理由）」を書く。修正は次の固定操作だけで行い、自由な「潤色」はしない。

| 検出された型 | 固定操作 |
|---|---|
| 譲歩式自弁（〜ではあるが有効／概ね問題ないかと存じますが〜の可能性も） | 結果＋境界＋未検証範囲の三要素に置換 |
| 審査式話語（確認済み／検証済み／多角的に検証した） | 削除。残す価値があるなら仕様・観察・境界のどれかに書き換え |
| 背景反復・手順再生・パラメータ堆積 | 一文の結果インターフェースに圧縮 |
| 証拠のない強い語（確実に／必ず／問題ありません） | 証拠のある強さに降格するか、証拠を補う |
| 根拠のないぼかし（かもしれない／と思われる／かと存じます） | 本文に証拠があれば断定、なければ【要確認】標識 |
| 一文多役 | 分割し各文に一役 |
| 翻訳調・敬語の誤り・字形 | 表層目録に従い母語の形に戻す |
| 前提・範囲・未検証項目 | 削除禁止。形式だけ整える |

修正後、Lane 0 を再実行し、変更した文だけを対象に第2ラウンド（新しいサブエージェント）を回す。新規 finding が出なければ終了。2ラウンド回しても同じ finding が再発するなら、規則でなく素材（証拠・数値）の不足なので、書き足す前に情報収集へ戻る。

## 3. 実行モード

- **quick（既定）**：Lane 0 ＋ サブエージェント1体（A・B・C を節分けで一括）＋ 1ラウンド。チャット回答・メール・社内メモ。追加時間は1〜2分。
- **full**：Lane 0 ＋ 並列サブエージェント3体 ＋ 2ラウンド。顧客に渡す資料、経営向け、対外文書、1万字超。開始時に所要時間（5〜15分）をユーザーに一言伝える。
- 迷ったら quick で仕上げて「full で磨き直せる」と添える。full と決めたら短い文書でも工程を省かない。

呼び出し例：`/ja-output-quality full review 回答案.md`、`/ja-output-quality write 顧客向けの回答を作る`（write は1章の憲法で書き、完成後に自動で review へ進む）。

## 4. 度量と回流 — 事後修正を生成時制約へ戻す

- 文書ごとに記録する：日付・文書型・Lane 0 の findings 密度（件/1000字）・各 Lane の判定・最頻の型。チャット内の一覧で足りる。
- 同じ型が3文書以上で再発したら、その型は「検出して直す」対象から「生成時に禁じる」対象へ昇格させる。昇格先は責任のある体裁スキル（顧客回答なら customer-qa-style の実例、レポートなら natural-japanese の doctype）か、`scripts/ja_lint.py` の規則。
- 良い実例を集める。顧客に通った文章を、文書型ごとに3〜5本、before/after の形で体裁スキルの examples に追加する。実例は禁止語の一覧より効く。
- スキル自体の改善は skill-creator の eval で行う。同じ依頼を「本スキルあり/なし」で走らせ、Lane 0 の密度と Lane B の FAIL 数で比較する。

## 5. 他スキルとの接続

- 常時適用したい規則（憲法の圧縮版）は `assets/global-rules.md` を `~/.claude/CLAUDE.md`（Claude Code）と claude.ai の個人設定（プロフィール／プロジェクト指示）に貼る。スキルが発火しない短い回答にも効く。
- 各体裁スキルの末尾に接続行を足す。文面は `assets/integration.md`（customer-qa-style・natural-japanese・japanese-tech-writing・その他向けの差分を用意）。
- customer-qa-style の Step 5 セルフチェックは、Lane B への入力チェックリストとして残し、判定はサブエージェントに移す。書き手が自分で「制約ゼロのできるはない」と点検するより、別コンテキストに「制約のない『可能』を列挙せよ」と命じるほうが漏れない。

## 6. 表層目録

`references/ja-surface.md`（natural-japanese と japanese-tech-writing への委譲先、翻訳調の最頻型、顧客向け敬語の型、字形・記号）。毎回読まない。Lane C の finding で判断に迷ったときと、full モードの執筆前にだけ開く。

## 7. 後片付け

台帳・lint の JSON・サブエージェントの所見は作業用の一時物であり、ユーザーの成果物ディレクトリに残さない。残すのは完成した文書だけ。
