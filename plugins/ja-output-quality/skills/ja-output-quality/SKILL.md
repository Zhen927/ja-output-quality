# ja-output-quality — 日本語文書の共通品質ルールとレビュー

体裁（段落か箇条書きか、敬体か常体か、番号の振り方）は体裁を決めるスキルに任せる。このスキルは体裁に口を出さず、どんな体裁でも守るべき五つだけを扱う。**内容が正しい。主張の強さが根拠に見合っている。読み手が判断できる材料が揃っている。読みやすい。自然な日本語で、相手に合った言葉遣いになっている。**

対象は、IT・SI・プリセールスの現場で顧客に渡す技術回答、提案書、報告書と、その周辺の社内文書である。学術論文向けの規範ではない。確度の書き分けは customer-qa-style が定める「確認済みの事実は断定、実測は条件付き、解釈は『〜という認識』、推測は根拠つき、将来は『見込み』」に合わせる。

既存スキルとの分担は次のとおり。natural-japanese は文書の型と表現、japanese-tech-writing は論の運び、customer-qa-style は顧客回答の体裁。このスキルはその土台になる共通ルールと、書き手から切り離したレビューを受け持つ。

## 0. 前提 — ルールを書くだけでは直らない理由

1. AI の日本語が読みにくい原因は三つに分かれる。英単語に辞書の訳語を当てただけの語（「コストを解消する」）、英語の文構造のままの言い回し、そして長く凝った表現を好む生成のくせ。知識が足りないから起きるのではなく、参考資料を増やしても再発する。
2. CLAUDE.md に書いたルールは、会話が長くなると過去のやり取りの側に沈み、直近の指示に押し負ける。ルールは「お願い」にすぎず、書いた文をルールと照合する工程がなければ守られるかどうかは毎回の確率になる。
3. 書いた本人は、同じ会話の中では自分の文を審査できない。同じモデルで読み直しても同じ判断が再生される。しかも同じ系統の強いモデルは、自分が書いた直訳調を「馴染んだ文」として見過ごす。読みやすさの判定は、書き手とコンテキストを共有しない別の、むしろ弱いモデルに向いている。判定するのは内容の正しさではなく「読んで引っかかるか」なので、深い思考力は要らない。
4. ルールは増やすほど守られなくなる。書く前に持たせるルールは10か条までにし、残りは機械チェックとレビューに逃がす。良い実例1本のほうが禁止語50個より効く。
5. 予防線と言い過ぎは同じ欠陥である。主張の強さが根拠に見合っていないだけで、弱すぎるか強すぎるかの違いしかない。どちらも「結果＋条件＋確認していない範囲」という同じ直し方で直る。
6. 最初から日本語で書く。英語で考えてから訳さない。用語は日本の業務で普通に使う言葉を選び、直訳の造語を作らない。目安は「その言葉を同僚に口頭で言えるか」。
7. 門番が厳しいと、AI は検査の入る Write／Edit を避けて Bash のヒアドキュメントに逃げる。文書は Write／Edit で書くよう決めておく。LLM に「この仕組みを入れるべきか」と聞いても当てにならない。入れて、動きを見て判断する。

## 1. 書く前のルール10か条

書き始める前に読む。体裁は決めない。同じ内容が `assets/global-rules.md` にあり、プラグイン版ではセッションの開始・再開・compact のたびに自動で注入される。

1. **結論を最初に書く。** 前置き、予告、お礼、「いよいよ」のような飾りの前置き、「この章が最も重要です」のような文章自身についての文は書かない。
2. **主張の強さは根拠に合わせる。** 「かもしれない」「と思われる」「かと存じます」は何が不確かなのか言えるときだけ、「確実に」「必ず」「問題ありません」は根拠を指せるときだけ使う。どちらも言えないなら「結果＋条件＋確認していない範囲」の形で書く。前提、適用範囲、未確認の項目は削らない。
3. **内容そのものを書き、作業の経過を書かない。** 「確認済み」「検証済み」「多角的に検証した」「AIとして」「私は〜を確認した」、「〜を見てみます」「〜はこうなっています」のような実況は本文に入れない。書いてよいのは、何が保証されているか、何を実際に確かめたか、どこまで当てはまるか、の三つ。
4. **一文に役割は一つ。** 「つまり〜」の言い直し、背景の繰り返し、手順のなぞり、「意外と知られていませんが」のような読者の反応の決めつけは書かない。削っても失われる情報がない文は書かない。
5. **確度を書き分ける。** 公式ドキュメントで確認した事実は断定して出典を添える。検証環境や過去案件での実測は条件を添える。解釈は「〜という認識」、推測は「〜と思われる（根拠: 〜）」、将来は「〜の見込み」と書き、プレビューと GA を区別する。事実が足りないときは想像で書かず、書く前に聞く。確認できなかったことは【要確認】。
6. **数値には条件と幅を付ける。「できる」には制約を添える。** ラベルや見出しに説明を添えるときは、なぜそのラベルに当たるのかまで書く（「堅牢性: リトライ処理あり」ではなく「堅牢性: 通信が一時的に失敗しても、リトライで処理が最後まで完了する」）。
7. **最初から日本語で書く。** 英単語に辞書の訳語を当てただけの語（「コストを解消する」→「削減する」）、無生物主語＋他動詞、「〜することができる」「〜において」「〜を行う」の名詞化を避ける。硬い漢語より平易な言葉、くだけた語や造語・略語は使わない。業界で定着した用語はそのまま使う。新しい用語は読者が知っている概念で言い換えてから使う。一覧は `references/ja-surface.md`。
8. **構成は、1節に1テーマ、1段落に1主張。** 段落の最初の文で主張を示す。原因や条件を先に、結果を後に書く。追記や改稿の前に前後と関連する節を読み直し、重複と「前述の」が指す先のない接続を作らない。どこも同じ厚みにせず、同じ型を3回続けない。
9. **強調は中身で行う。** チャットの回答に見出しや番号付きの章立てを付けない（見出しはファイルに書く長い文書だけ）。ルールの条文や観点名、フックの指摘を回答に引用しない。太字は段落に1か所まで。絵文字、感嘆符、「非常に」「極めて」「圧倒的」は使わない。地の文の文を体言止めにしない（箇条書きの体言止めは体裁スキルに従う）。主語や目的語が文脈から分からない文では省かない。「状態保持」のような名詞化した用語は、主語と動詞のある文にする。
10. **顧客向けは敬語のルールを守る。** 二重敬語は使わない。「させていただく」は許可や恩恵がある場面だけ。「〜になります」「〜のほう」は使わない。クッション言葉は一通に1回。文書では「貴社」、会話では「御社」。全角英数、半角句読点、簡体字を混ぜない。外部ドキュメントを参照して書くときは原文を貼らず、理解してから自分の言葉で書く。

**優先順位**：体裁スキルの体裁ルール ＞ このスキルの体裁に関する助言。このスキルの2・3・5条（根拠との釣り合い、作業報告の排除、確度の書き分け）＞ どのスキルの表現上の好みよりも優先。迷ったら、読み手の得になるほうを選ぶ。

## 2. 三つの層で守る — ルールの再注入、書き込み前の門番、完成時のレビュー

ルールを書くだけでは守られないので、生成の外側に三つの仕組みを置く。プラグイン版では①②とターン終了時の判定が `hooks/hooks.json` として同梱され、導入するだけで動く。

| 層 | 仕組み | いつ | 判定するモデル |
|---|---|---|---|
| ① ルールの再注入 | SessionStart フック | セッションの開始・再開・/clear・compact のたび | なし（`assets/global-rules.md` をそのまま注入） |
| ② 書き込み前の門番 | PreToolUse のプロンプト型フック | .md／.txt を Write／Edit する直前 | Haiku（プロンプト型フックの既定。速く、安く、書き手と別のモデル） |
| ③ 完成時のレビュー | このスキルの review（観点A・B・C） | 文書を書き終えたとき | Haiku 4.5（quick は effort medium、full は effort max） |
| 補 ターン終了時の判定 | Stop のプロンプト型フック | 最終回答に200字以上の日本語があるとき | Haiku |
| 補 生成した文書の本文チェック | PostToolUse のコマンド型フック（`scripts/office_text.py`） | Bash で .pptx／.xlsx／.docx を作った直後 | なし（本文を抜き出して `ja_lint.py` にかける） |

②の対象は .md、.txt、.html（pptx スキルがスライドの原稿に使う）。PowerPoint、Excel、Word は Bash のスクリプトで生成されるので②では止められない。そのため、本文を先に .md の原稿として書かせて②を通し、生成後に本文を抜き出して機械チェックにかける。抜き出した本文は一時ファイルに保存され、パスが通知されるので、顧客に渡すものはそれを `/ja-output-quality review` にかける。

②は違反があると書き込み自体を拒否し、理由を書き手に返す。書き手は同じターン内で直して書き直す。同じ編集が3回続けて拒否されたら止まってユーザーに相談する。判定不能やタイムアウトのときは素通し（fail open）にして、文章チェックのために作業が止まらないようにする。迷ったら指摘する（見逃しより過検知を許容する）。

**モデルの決まり（必須）**：レビューや判定のサブエージェントは、セッションのモデルを引き継がない。同梱のレビュー担当は frontmatter でモデルと effort を固定してあるので、これを `subagent_type` に指定して起動する。名前はプラグイン版が `ja-output-quality:reviewer`、`ja-output-quality:check-sentences`、`check-evidence`、`check-wording`、`install-local.sh` で入れた版が `ja-output-quality-reviewer`、`ja-output-quality-check-sentences`、`ja-output-quality-check-evidence`、`ja-output-quality-check-wording`。利用できるエージェントの一覧にあるほうを使う。同梱エージェントが見えない環境（claude.ai の Cowork、zip 版スキルだけの Web セッション）では、Agent ツールに `model: "haiku"` を明示し、`references/review-protocol.md` のプロンプトを渡す。モデルを指定せずに起動しない。書き手（親）はセッションのモデルのままでよい。

書き終えた文章のレビュー（③）の要点は次のとおり。プロンプトと出力形式は `references/review-protocol.md`。

**機械チェック（lint）**
- 主：natural-japanese の `scripts/lint.py --json`（uv がある環境。常套句、翻訳調、体言止めの割合、段落構成、語彙の偏り）。
- 補：このスキルの `scripts/ja_lint.py --json <file>`（標準ライブラリだけで動く。敬語、作業報告の混入、語尾のぼかし、条件のない「できる」、幅のない数値、ラベルのない未確認事項、文字種と記号）。uv がない環境ではこちらだけで回す。
- 検出結果は「疑い」であって指示ではない。すべて判断台帳に載せ、直すか残すか（理由つき）を決める。

**観点A 文の要否と構成** 一文ごとに役割（主張／根拠／条件／つなぎ／作業報告／飾り／重複）を付け、予防線、作業報告の混入、説明過多、文体の癖、飾り、同じ型の繰り返しを判定する。文書全体を読み、重複、接続の乱れ、構成の崩れも見る。
**観点B 根拠** 主張の文だけを抜き出し、確度の種類（公式ドキュメントで確認済みの事実／検証環境や過去案件での実測・実績／自分の解釈・経験則／推測／将来の見込み）と書き方が合っているか、根拠が本文か参照範囲の中にあるか、条件のない「できる」や幅のない数値がないか、限られた実測を一般化していないか、「できる」と「使うべき」を分けているかを判定する。
**観点C 表記と言葉遣い** 語彙と構文の直訳、直訳の造語、硬い漢語やくだけた語、敬語、文字種と記号を判定する。

**レビュー担当がしてはいけないこと**：書き直す、原文をかばう、褒める、要約する。出力は「原文の文 ／ 種類 ／ 判定（削除・修正・保留） ／ 直し方の指示（何を補うか。文案は書かない）」の行だけ。最後に各観点 の判定を 合格／注意／不合格 で書く。

**書き手（親）の仕事**：三つの観点 の指摘と 機械チェック の検出結果を一つの判断台帳にまとめ、指摘ごとに「直した」か「残す（理由）」を書く。直すときは次の決まった直し方だけを使い、自由に「整える」ことはしない。

| 指摘の種類 | 直し方 |
|---|---|
| 予防線（〜ではありますが有効／概ね問題ないかと存じますが〜の可能性も） | 結果＋条件＋確認していない範囲の三つに置き換える |
| 作業報告の混入（確認済み／検証済み／多角的に検証した） | 削除する。残す価値があるなら、仕様・実測・条件のどれかに書き換える |
| 背景の繰り返し、手順のなぞり、パラメータの羅列 | 結果を一文にまとめる |
| 根拠のない断定（確実に／必ず／問題ありません） | 根拠に見合う強さに下げるか、根拠を足す |
| 根拠のないぼかし（かもしれない／と思われる／かと存じます） | 本文に根拠があれば言い切る。なければ【要確認】を付ける |
| 一文に役割が複数 | 文を分け、それぞれ一つの役割にする |
| 翻訳調、敬語の誤り、文字種の混在 | 一覧に従って直す |
| 重複、接続の乱れ、構成の崩れ | 重複は片方を削る。「前述の」の指す先を作るか外す。別のテーマは別の節へ移す |
| 前提、適用範囲、未確認の項目 | 削らない。表現だけ整える |

直すときは、注記や補足の追記で逃げず、問題のある本文そのものを書き直す。直した文書は元より短いか同じ長さに保つ。

直したら機械チェックをもう一度回して終わり。レビューは quick も full も1回だけで、2回目のサブエージェントは起動しない。機械チェックに新しい指摘が出たときや、指摘の理由が材料（根拠や数値）の不足にあるときは、文をいじり続けず、何を確かめれば書けるかをユーザーに返す。

## 3. 実行モード

- **quick（既定）**：機械チェック ＋ reviewer 1体（観点A・B・C をまとめて担当、Haiku 4.5、effort medium）＋ 1回。チャットの回答、メール、社内メモ向け。追加の時間は1〜2分。
- **full**：機械チェック ＋ check-sentences、check-evidence、check-wording の並列3体（いずれも Haiku 4.5、effort max）＋ 1回。顧客に渡す資料、経営層向け、社外文書、1万字を超える文書向け。始める前に、かかる時間の目安（3〜5分）をユーザーに一言伝える。
- 迷ったら quick で仕上げ、「full で磨き直すこともできる」と添える。full と決めたら、短い文書でも手順を省かない。

呼び出し例：`/ja-output-quality full review 回答案.md`、`/ja-output-quality write 顧客向けの回答を作る`（write は1章のルールで書き、書き終えたら自動で review に進む）。

## 4. 計測とフィードバック — 直した結果を「書く前のルール」に戻す

- 文書ごとに記録する。日付、文書の種類、機械チェック の検出数（件／1000字）、各観点 の判定、いちばん多かった指摘の種類。チャット内の一覧で足りる。
- 同じ種類の指摘が3文書以上で繰り返されたら、「検出して直す」ものから「書く前に禁じる」ものに格上げする。格上げ先は、責任のある体裁スキル（顧客回答なら customer-qa-style の実例、レポートなら natural-japanese の文書型）か、`scripts/ja_lint.py` のルール。
- 良い実例を集める。顧客に通った文章を、文書の種類ごとに3〜5本、修正前後の形で体裁スキルの実例集に足す。実例は禁止語の一覧より効く。
- 門番と判定の運用は次の決まりで回す。判定不能やタイムアウトは素通し（fail open）。差し戻しは3回で打ち切り、ユーザーに相談する。書き込みのたびに全文を判定せず、判定は「書き込む直前」「ターンの終わり」「完成時」の三点に絞る。迷ったら指摘する。素通りした違反を見つけたら、門番のプロンプト（`hooks/hooks.json`）に基準を一つ足す。
- スキル自体の改善は skill-creator の評価機能で行う。同じ依頼を「このスキルあり／なし」で走らせ、機械チェック の検出数と 観点B の不合格数で比べる。

## 5. 書かせる前にすること、他のスキルとのつなぎ方

- **書かせる前に論点を整理する。** 読みにくい文章の多くは、文面ではなく内容が整理されていないことから来る。顧客への回答や提案は、書く前に grill-me で前提と論点を詰め、customer-qa-style の Step 1〜3（論点の分解、事実確認）を終えてから書く。
- **一次情報を引用させる。** 公式ドキュメントの該当箇所、検証環境の実測値、社内の過去案件の記録など「そこにしかない事実」を引用して書かせる。推測で埋めた文が減るほど読みやすくなり、誤りも減る。
- **Advisor を使う。** Claude Code の `/advisor` は、本体より能力の高いモデルを相談役に指定したときだけ動く。本体が Fable 5.1 のときは使えないので、本体を Sonnet 5 にして `/advisor fable` か `/advisor opus` とする使い方になる。
- **ルールの常時適用**。プラグイン版は SessionStart フックで `assets/global-rules.md` を自動注入する。claude.ai（Cowork、Web セッションの zip 版）にはフックがないので、同じ内容を個人設定（プロフィール、プロジェクトの指示）に貼る。
- **体裁スキルとの併用**。各体裁スキルの末尾に併用の一文を足す。文面は `assets/integration.md`。customer-qa-style の Step 5 セルフチェックは、観点B に渡すチェックリストとして残し、判定はサブエージェントに移す。
