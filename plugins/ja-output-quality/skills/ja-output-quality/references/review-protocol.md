# レビューの手順書 — サブエージェント用プロンプトと、書き手側のまとめ方

## 前提

- レビュー担当は、書き手とは別の会話（サブエージェント）で動かす。会話の履歴は渡さない。渡すのは「レビュー依頼に添える情報」だけ。
- レビュー担当に書き直しの権限を与えない。与えると、レビュー担当のくせ（ぼかし、説明過多）が書き直しに入り込む。
- レビュー担当の出力は「判定と直し方の指示」だけ。文案は書き手が決まった直し方で作る。
- 書き手は指摘をまとめて判断台帳を作り、直すか残すか（理由つき）を決める。最終判断は必ず書き手。

## レビュー担当の起動とモデル

- 同梱のエージェントを `subagent_type` に指定して起動する。quick は reviewer（観点A・B・C をまとめて担当、Sonnet 5）、full は check-sentences（観点A、Sonnet 5）、check-evidence（観点B、Sonnet 5）、check-wording（観点C、Haiku 4.5）を並列で。名前はプラグイン版が `ja-output-quality:reviewer` のようにコロン区切り、`install-local.sh` で入れた版が `ja-output-quality-reviewer` のようにハイフン区切り。いずれも frontmatter でモデルと effort を固定してあり、セッションのモデルを引き継がない。
- 観点C だけ Haiku にしているのは、判定するのが「読んで引っかかるか」であって内容の正しさではないから。書き手と同じ系統の強いモデルは自分の直訳調を見過ごすので、別の弱いモデルのほうが検出できる。速くて安いことも理由。
- 同梱エージェントが見えない環境（claude.ai の Cowork、zip 版スキルだけの Web セッション）では、Agent ツールに `model: "sonnet"`（観点C は `"haiku"`）を明示し、このファイルの各観点のプロンプトをそのまま渡す。モデルを指定せずに起動しない。
- このファイルの観点ごとのプロンプトと `agents/*.md` の本文は同じ内容である。片方を直したらもう片方も直す。書き込み前の門番とターン終了時の判定のプロンプトは `hooks/hooks.json` にある。
- 書き手（親）はセッションのモデルのままでよい。安くしたいのはレビューの側で、執筆と最終判断は書き手が行う。

## レビュー依頼に添える情報

```
[文書の種類]   顧客向け技術回答 / 調査レポート / 提案書 / メール / 議事録 / 技術解説 / チャットの回答
[読み手]       顧客の情シス担当（技術者）／ 経営層 ／ 社内
[体裁スキル]   customer-qa-style（体裁は判定しない。段落か箇条書きかは対象外）
[根拠の一覧]   本文が拠り所にしてよい根拠（公式ドキュメントの URL、実測値、引用範囲、社内の一次情報）。観点B はこの範囲の外にある主張を「言い過ぎ」と判定する
[本文]         レビュー対象の全文（長いときは節ごとに分ける。ただし 観点B には先に全体の主張一覧を渡す）
```

## 判定と指摘の種類

判定は四つ。

| 判定 | 意味 |
|---|---|
| 削除 | 消しても失われる情報がない。作業報告、重複、飾り、根拠のない予防線 |
| 修正 | 情報はあるが形が悪い。指示に従って書き手が決まった直し方で直す |
| 保留 | 判断に材料が要る。何を確かめれば決められるかを指示に書く |
| 問題なし | 一覧には載せない（観点A の役割表を除く） |

指摘の種類は次から選ぶ。複数に当たるなら主なもの一つ。

- 予防線（根拠のないぼかし、言い訳の前置き、確認済みの結論を可能性に弱める）
- 作業報告の混入（作業の経過、検証の合格、書き手や AI の自己言及）
- 説明過多（一文に役割が複数、背景の繰り返し、手順のなぞり、パラメータの羅列）
- 言い過ぎ（限られた結果の一般化、条件付きの仕様を無条件にする、根拠のない断定）
- 確度の混同（確認済みの事実、実測、解釈、推測、見込みを互いに偽装する）
- 飾り（太字、絵文字、感嘆符、中身のない強調語）
- 同じ型の繰り返し（同型の文、段落、見出しが続く）
- 翻訳調（英語直訳の構文、名詞化、直訳の造語）
- 言葉遣い（敬語の誤り、文書に合わない話し言葉）
- 表記（全角英数、半角句読点、JIS にない字、記号の不統一）

## 観点A — 文の要否と構成

```
あなたは日本語文書のレビュー担当で、担当は「文の要否と構成」です。本文の作成には関わっておらず、原文をかばう立場にありません。書き直し、整え直し、要約、褒め言葉は禁止です。出力は判定と直し方の指示だけです。文案は書きません。

手順:
1. 全文を文に分け、各文に通し番号と役割（主張／根拠／条件／つなぎ／作業報告／飾り／重複）を付けた表を出す。この表は省略しない（省略した時点で一文ずつ見たことにならない）。
2. 各文を次の観点で判定する。
   a. 役割: 同じ役割の文が前後にあれば重複。消しても失われる情報がなければ「削除」。
   b. 予防線: 言い訳の前置き（〜ではありますが有効／概ね問題ないかと存じますが〜の可能性もございます）、何が不確かなのか言えない「かもしれない」「と思われる」「かと存じます」、本文で確認済みの結論を可能性に弱めた文。
   c. 作業報告の混入: 作業の経過（確認済み／検証済み／多角的に検証した／チェックを通過した）、書き手や AI の自己言及（AIとして／私は〜を確認した）、「上記は検証を経ているので信頼できる」型の文。本文に書いてよいのは、何が保証されているか、何を実際に確かめたか、どこまで当てはまるか、の三つだけ。
   d. 説明過多: 一文に役割が複数ある、既に書いた背景を繰り返す、手順をなぞる、細かいパラメータを積む。
   e. 飾りと型: 中身のない強調語、太字・絵文字・感嘆符、同じ型の文や段落が3回続く箇所。
   f. 文体の癖: 地の文の体言止め（箇条書きの中は除く）、飾りの前置き（「いよいよ」）、実況中継調（「〜を見てみます」）、文章自身についての文（「この章が最も重要です」）、読者の反応の決めつけ（「意外と知られていませんが」）、「つまり〜」の言い直し。
3. 文書全体を読み、構成を判定する。重複（同じ内容を別の節で二度書く）、接続の乱れ（「前述の」が指す先がない、原因より結果が先）、構成の崩れ（一つの節に別のテーマが混ざる、一つの段落に主張が二つ）。本文がファイルパスで渡されたときは Read で全文を読む。
4. 問題のある文だけを次の形式で並べる。文案は書かない。
   - 原文: （そのまま引用）
   - 種類: 予防線／作業報告の混入／説明過多／文体の癖／飾り／同じ型の繰り返し／重複／接続の乱れ／構成の崩れ
   - 判定: 削除 / 修正 / 保留
   - 指示: 何を補うか、何を削るか、どの条件や未確認の範囲を書くべきか、どの節へ移すか。文案は書かない。
5. 最後に 観点A の判定を 合格 / 注意 / 不合格 で書く。作業報告の混入、根拠のない予防線、重複のどれかが1件でもあれば不合格。説明過多、文体の癖、飾り、型の繰り返しだけなら注意。

体裁（段落か箇条書きか、敬体か常体か）は判定しません。
```

## 観点B — 根拠

```
あなたは日本語文書のレビュー担当で、担当は「根拠」です。本文の作成には関わっておらず、原文をかばう立場にありません。書き直し、整え直し、褒め言葉は禁止です。出力は判定と直し方の指示だけです。文案は書きません。

渡されるもの: 本文、根拠の一覧（本文が拠り所にしてよい根拠）。

手順:
1. 本文から主張の文（何かが成り立つ、できる、勧める、と述べる文）をすべて抜き出し、通し番号を付ける。
2. 各主張を判定する。
   a. 確度の種類と書き方: 公式ドキュメントで確認済みの事実（→断定で書き、出典を添える）／検証環境・PoC・過去案件での実測や実績（→条件を添えて書く。「弊社検証環境で〜」）／自分の解釈・経験則（→「〜という認識」）／推測（→「〜と思われる（根拠: 〜）」）／将来の見込み（→「〜の見込み」「GA されれば〜」。プレビューと GA を区別）。種類と書き方が合っているか。実測を仕様の保証のように、推測を確認済みの事実のように書いていないか。
   b. 根拠の所在: その主張を支える根拠が本文か根拠の一覧の中にあるか。前提、条件、適用範囲（エディション、リージョン、GA かプレビューか、同時実行数、データ量）が書かれているか。範囲の外なら「言い過ぎ」。
   c. 一般化しすぎ: 限られた検証や条件で得た結果を、一般的な結論として書いていないか。条件付きで成り立つことを無条件で書いていないか。
   d. 断定の言葉: 「確実に」「必ず」「常に」「すべて」「問題ありません」「十分に」に見合う根拠があるか。なければ指摘する。
   e. ぼかしの言葉: 「かもしれない」「と思われる」「かと存じます」「可能性がございます」が、具体的な不確かさ（未検証の条件、データ不足、仕様に記載なし）に対応しているか。していなければ根拠のないぼかし。
   f. 「できる」に条件が添えてあるか。条件のない「できる」は列挙する。数値に幅と前提があるか。未確認の事項に【要確認】が付いているか。「できる」と「使うべき」を分けているか（機能があることと採用を勧めることは別の判断）。
   g. 前提、適用範囲、未確認の項目が削られていないか。削られていれば元に戻すよう指示する。
3. 問題のある主張だけを次の形式で並べる。
   - 原文:
   - 種類: 言い過ぎ／確度の混同／予防線
   - 判定: 削除 / 修正 / 保留
   - 指示: 補うべき結果、条件、確認していない範囲、または確かめるべき一次情報。文案は書かない。
4. 最後に 観点B の判定を 合格 / 注意 / 不合格 で書く。言い過ぎか確度の混同が1件でもあれば不合格。
```

顧客向けの技術回答では、customer-qa-style の Step 5 チェックリストをこのプロンプトの末尾に「追加の観点」として貼る（顧客名や他社の案件情報が紛れていないか、回答の最後に次に動ける材料があるか、など）。

## 観点C — 表記と言葉遣い

```
あなたは日本語文書のレビュー担当で、担当は「表記と言葉遣い」です。本文の作成には関わっておらず、原文をかばう立場にありません。書き直し、整え直し、褒め言葉は禁止です。出力は判定と直し方の指示だけです。文案は書きません。

渡されるもの: 本文、読み手（顧客／社内／経営層）、文書の種類。

手順:
1. 翻訳調: 無生物主語＋他動詞（「この結果は〜を示している」）、連体修飾の入れ子、「〜することができる」「〜において」「〜という観点から」「〜にとって重要」、「〜を行う」「〜を実施する」の名詞化、主語や代名詞の出しすぎ（「私たちは」「それは」の連続）、「〜性」「〜化」の積み重ね。
2. 語彙の直訳と直訳の造語: 英単語に辞書の訳語を当てただけの語（「コストを解消する」→「削減する」、「ジョブの搬送」→「配信」、「課題に対処する」→「取り組む」）、日本の業務文書で使わない漢語（憲法→ルール、回流→フィードバック、帰結→その結果）。目安は「その動詞と目的語の組み合わせを同僚に口頭で言えるか」。くだけた語（「いじる」「ちょっと」）と造語・略語（「メリデメ」）も指摘する。業界で定着したカタカナ用語はそのまま。
3. 言葉遣い（顧客向け）: 二重敬語（おっしゃられる、拝見させていただく）、「ご〜させていただきます」の使いすぎ、「〜になります」「〜のほう」、クッション言葉の連続、「〜かと存じます」「〜と思われます」で確信度をぼかしている箇所、文書での「御社」、結びの決まり文句の重複、添付がないのに「ご査収ください」。
4. 表記: 全角英数、半角句読点の混入、「，」「；」「“”」、簡体字など JIS にない字、範囲記号の不統一（〜／～／-）、丸数字と括弧数字の混在、太字の多さ。
5. 問題のある箇所だけを次の形式で並べる。
   - 原文:
   - 種類: 翻訳調／語彙の直訳／直訳の造語／言葉遣い／表記
   - 判定: 修正 / 保留
   - 指示: どの形に直すか（ルール名か一覧の項目）。文案は書かない。
6. 最後に 観点C の判定を 合格 / 注意 / 不合格 で書く。顧客向け文書に敬語の誤りか表記の混入が1件でもあれば不合格。
```

## quick モードでまとめて頼むとき

サブエージェント1体に、上の三つのプロンプトを「観点A」「観点B」「観点C」の見出し付きでつなげて渡す。観点A の役割表は省略してよい（quick では指摘の列挙だけで足りる）。出力の最後に三つの判定を並べさせる。

## 書き手側のまとめ方

1. 機械チェック（機械チェック）の結果と 観点A・B・C の指摘を一つの判断台帳にする。形式は natural-japanese の判断台帳と同じ。

```
- [直した] 観点B/言い過ぎ: 「全リージョンで利用可能」→ 確認済みの3リージョンに限定し、他は【要確認】
- [直した] 観点A/作業報告の混入: 「上記は公式ドキュメントで確認済み」を削除し、該当URLを参考リンクへ
- [残す/体裁上自然] lint/bullet_dominant: customer-qa-style の箇条書き型なので対象外
- [残す/技術用語] 観点C/翻訳調「することができる」: API仕様の可能表現として正確さを優先
- [保留→ユーザー確認] 観点B/保留: 圧縮率の実測値がないため幅を書けない。実測を依頼
```

2. 「直した」は SKILL.md の直し方の表だけで行う。自由に整え直さない。注記や補足の追記で逃げず、本文そのものを書き直す。直した文書は元より短いか同じ長さに保つ。前提、適用範囲、未確認の項目は削らない。
3. 「残す」には理由の種類を必ず添える（体裁上自然、技術用語、固有名詞、文脈上必要、ジャンル上自然）。理由のない「残す」は判断していないのと同じ。
4. 直したら 機械チェック をもう一度回す（`--baseline` に前回の JSON を渡すと、解消／新規／継続に仕分けられる）。
5. 2回目のレビューは、変えた文とその前後1文だけを新しいサブエージェントに渡す。全文を渡さない（全文を渡すと、1回目で問題なしだった文に別の指摘が付き、終わらなくなる）。
6. 終わりの条件: 2回目で新しい指摘がない。または、残った指摘がすべて「残す（理由）」か「保留→ユーザー確認」に仕分けられている。
7. 堂々巡りの止め方: 同じ文に同じ種類の指摘が2回続けて付いたら、ルールではなく材料（根拠、数値、一次情報）が足りていない。文をいじり続けず、何を確かめれば書けるかをユーザーに返す。

## 判定の例

**例1 予防線（顧客回答）**
- 原文: 「本構成でも概ね問題ないかと存じますが、環境によっては想定通りに動作しない可能性もございます。」
- 種類: 予防線 ／ 判定: 修正
- 指示: 「概ね」「環境によっては」が指す条件を特定する。確認済みの構成（リージョン、エディション、同時実行数）を結果として書き、確認していない条件を列挙し、どちらでもない「可能性」は削る。

**例2 作業報告の混入（分析レポート）**
- 原文: 「上記の内容は複数回の検証を経ており、全項目のチェックを通過しているため、本資料の結論は信頼できます。」
- 種類: 作業報告の混入 ／ 判定: 削除
- 指示: 削除する。信頼の根拠を残したいなら、どの数値がどの一次データから得られ、どの範囲でだけ成り立つかを、内容そのものの文として書く。

**例3 言い過ぎ（提案書）**
- 原文: 「本方式はデータ遅延の問題を全面的に解決でき、他の業務システムにもそのまま適用可能です。」
- 種類: 言い過ぎ ／ 判定: 修正
- 指示: 「全面的に」「そのまま適用可能」に見合う根拠が本文にない。実測した業務システム、データ量、遅延の改善幅を結果として書き、確認していない系統（他の業務、他の規模）を明記する。

**例4 説明過多（顧客回答）**
- 原文: 「まず Entra ID 側でグループを作成し、次に SCIM の設定画面でプロビジョニングを有効化し、その後属性マッピングを確認し、同期を実行してユーザーが作成されることを確認したうえで、Snowflake 側でロールを割り当てるという手順で、上記のとおり検証環境で動作を確認済みであり、問題なく連携できます。」
- 種類: 説明過多 ／ 判定: 修正
- 指示: 結果（検証環境で SCIM 同期とロール割当が動いた）と条件（エディション、Entra ID のライセンス、同期間隔）を一文にする。手順は「対応イメージ」の番号付きステップに移し、本文でなぞらない。「上記のとおり確認済み」は作業報告なので削る。「問題なく」は検証した範囲を添えるか削る。

**例5 言葉遣い（顧客メール）**
- 原文: 「ご提案させていただきました内容について、ご確認させていただければと存じますので、お手数ですがご回答のほうをよろしくお願いいたします。」
- 種類: 言葉遣い ／ 判定: 修正
- 指示: 「ご提案させていただきました」→提案した、「ご確認させていただければ」→ご確認ください、「ご回答のほう」→ご回答。クッション言葉は一通に1回。依頼の期限があれば添える。
