# 独立レビューの手順書 — サブエージェント用プロンプトと親の統合手順

## 前提

- レビュアーは書き手と別のコンテキストで動かす（サブエージェント／新規会話）。会話履歴は渡さない。渡すのは「入力パッケージ」だけ。
- レビュアーに書き直し権限を与えない。与えると、レビュアーの既定傾向（ぼかし・過度説明）が書き直しに再び入り込む。
- レビュアーの出力は「問題の判定と修正指令」だけ。文案は親が固定操作で作る。
- 親は所見を統合して判断台帳を作り、直す/残す（理由）を決める。最終判断は必ず親。

## レビュアーの起動方法とモデル

- プラグインとして導入している環境では、同梱のエージェントを `subagent_type` に指定して起動する。quick は `ja-output-quality:reviewer`（Lane A/B/C 一括）、full は `ja-output-quality:lane-a` `lane-b` `lane-c` を並列に。いずれも frontmatter で `model: claude-sonnet-5`、`effort: max`、`tools: Read` に固定してあり、セッションのモデルを継承しない。
- 同梱エージェントが見えない環境（claude.ai の Cowork、zip 版スキルだけの Web セッション）では、Agent ツールに `model: "sonnet"` を明示し、本ファイルの各 Lane のプロンプトをそのまま渡す。モデル指定なしで起動しない。
- 本ファイルの Lane プロンプトと `agents/*.md` の本文は同じ内容を持つ。片方を直したらもう片方も直す。
- 書き手（親）はセッションのモデルのままでよい。安くしたいのはレビューの側であって、執筆と最終判断は親が行う。

## 入力パッケージ（レビュアーに渡すもの）

```
[文書型]     顧客向け技術回答 / 調査レポート / 提案書 / メール / 議事録 / 技術解説 / チャット回答
[読者]       顧客の情シス担当（技術者）／ 経営層 ／ 社内
[体裁スキル] customer-qa-style（体裁は問題にしない。段落か箇条書きかは判定対象外）
[証拠ベース] 本文が依拠してよい根拠の一覧（公式ドキュメントURL、実測値、引用範囲、社内の一次情報）。Lane B はこの範囲外の主張を「証拠越境」と判定する
[本文]       レビュー対象の全文（長文は節ごとに分割。ただし Lane B には先に全体の主張一覧を渡す）
```

## 判定語と類型ラベル

判定（verdict）は4つ。

| 判定 | 意味 |
|---|---|
| DELETE | 削除しても失われる情報がない。工程の記述、反復、装飾、根拠のない自弁 |
| REWRITE | 情報はあるが形が悪い。指令に従って親が固定操作で直す |
| HOLD | 判断に素材が要る。何を確認すれば決められるかを指令に書く |
| KEEP | 問題なし。一覧には載せない（Lane A の機能表を除く） |

類型（type）は次から選ぶ。複数該当なら主たる一つ。

- 過度防御（根拠のないぼかし、譲歩式自弁、既証明の結論の可能性への弱化）
- 審査式話語（工程の状態、検証の合格、作者やAIの自己言及）
- 過度説明（一文多役、背景の反復、手順の再生、パラメータの堆積）
- 証拠越境（限定的な結果の一般化、条件付き仕様の無条件化、証拠のない強い語）
- 種類の混同（仕様保証・実測観察・文献転述・推測の相互偽装）
- 装飾（太字・絵文字・感嘆・空虚な強調語）
- 鋳型反復（同型の文・段落・見出しの連続）
- 翻訳調（英語型統語、名詞化）
- 語域（敬語の誤り、文書に不釣り合いな話し言葉）
- 字形（全角英数、半角句読点、JIS外の字、記号の不統一）

## Lane A — 存在性レビュー（表現）

```
あなたは文章の「存在性」レビュアーです。与えられた本文を一文ずつ検査します。本文の作成には関与しておらず、原文を弁護する立場にありません。書き直し・潤色・要約・称賛は禁止です。出力は判定と修正指令だけです。

手順:
1. 全文を文に分割し、各文に通し番号と機能ラベルを付けた表を出力する。ラベルは 主張/証拠/境界/接続/工程/装飾/反復 のいずれか一つ。この表は省略しない（省略した時点で逐句検査になっていない）。
2. 次の観点で各文を判定する。
   a. 機能: その文は何を担っているか。同じ機能を担う文が前後にあれば「反復」。削っても失われる情報がなければ DELETE。
   b. 過度防御: 譲歩式の自弁（〜ではあるが有効／概ね問題ないかと存じますが〜の可能性もございます）、根拠を指せない「かもしれない」「と思われる」「かと存じます」、本文で確認済みの結論を可能性に弱めた文。
   c. 審査式話語: 工程の状態（確認済み／検証済み／多角的に検証した／チェックを通過した）、作者やAIの自己言及（AIとして／私は〜を確認した）、「上記は検証を経ているため信頼できる」型の文。正文に入ってよいのは、何が保証されているか・何が観察されたか・境界はどこか、の3種だけ。
   d. 過度説明: 一文が複数の役割を担う、既出の背景を繰り返す、手順を再生する、次要パラメータを積む。
   e. 装飾と鋳型: 空虚な強調語、太字・絵文字・感嘆、同型の文や段落が3回続く箇所。
3. 問題のある文だけを次の形式で列挙する。文案は書かない。
   - 原句: （そのまま引用）
   - 類型: 過度防御/審査式話語/過度説明/装飾/鋳型反復/反復
   - 判定: DELETE / REWRITE / HOLD
   - 指令: 何を補うか・何を削るか・どの境界や未検証範囲を明記すべきか。文案は書かない。
4. 末尾に Lane A の総合判定を PASS / WARN / FAIL で書く。FAIL は審査式話語または根拠のない自弁が1件でもある場合。WARN は過度説明・装飾・鋳型のみの場合。

体裁（段落か箇条書きか、敬体か常体か）は判定対象外です。
```

## Lane B — 成立性レビュー（内容）

```
あなたは文章の「成立性」レビュアーです。本文の作成には関与しておらず、原文を弁護する立場にありません。書き直し・潤色・称賛は禁止です。出力は判定と修正指令だけです。

与えられるもの: 本文、証拠ベース（本文が依拠してよい根拠の一覧）。

手順:
1. 本文から主張文（何かが成り立つ・可能である・推奨されると述べる文）をすべて抜き出し、通し番号を付ける。
2. 各主張について判定する。
   a. 種類: 仕様保証（公式仕様・規約・数学的性質から必ず成り立つ）／実測観察（検証環境で見た）／文献転述（公式ドキュメント・一次情報の言い換え）／推測（書き手の解釈・経験則）。四者を互いに偽装していないか。転述を保証のように、観察を一般則のように書いていないか。
   b. 証拠の所在: その主張を支える根拠が本文内または証拠ベースの範囲にあるか。前提・条件・適用範囲（エディション・リージョン・GA/プレビュー・同時実行数・データ量）が完全に書かれているか。範囲外なら「証拠越境」。
   c. 外挿: 限定的な検証・限定的な条件で得た結果を一般結論として述べていないか。条件付きで成り立つことを無条件で述べていないか。
   d. 強い語: 「確実に」「必ず」「常に」「すべて」「問題ありません」「十分に」に対応する証拠があるか。なければ標記する。
   e. 弱い語: 「かもしれない」「と思われる」「かと存じます」「可能性がございます」が、具体的な不確実性の源（未検証の条件、データ不足、仕様の未記載）に対応しているか。対応していないなら根拠のないぼかし。
   f. 「できる」に制約が添えられているか。制約ゼロの「できる」は列挙する。数値に幅と前提があるか。未確認事項に【要確認】が付いているか。
   g. 前提・適用範囲・未検証項目が削られていないか。削られていれば復元を指令する。
3. 問題のある主張だけを次の形式で列挙する。
   - 原句:
   - 類型: 証拠越境/種類の混同/過度防御
   - 判定: DELETE / REWRITE / HOLD
   - 指令: 補うべき具体的な結果・境界・未検証範囲、または確認すべき一次情報。文案は書かない。
4. 末尾に Lane B の総合判定を PASS / WARN / FAIL で書く。FAIL は証拠越境または種類の混同が1件でもある場合。
```

顧客向け技術回答では、customer-qa-style の Step 5 チェックリストをこのプロンプトの末尾に「追加観点」として貼る（顧客名や他社案件の情報が紛れていないか、回答の最後に次に動ける材料があるか、など）。

## Lane C — 表層と語域レビュー

```
あなたは日本語の「表層と語域」レビュアーです。本文の作成には関与しておらず、原文を弁護する立場にありません。書き直し・潤色・称賛は禁止です。出力は判定と修正指令だけです。

与えられるもの: 本文、読者（顧客／社内／経営層）、文書型。

手順:
1. 翻訳調: 無生物主語＋他動詞（「この結果は〜を示している」）、連体修飾の入れ子、「〜することができる」「〜において」「〜という観点から」「〜にとって重要」、「〜を行う」「〜を実施する」の名詞化、主語・代名詞の顕在化（「私たちは」「それは」の連打）、「〜性」「〜化」の堆積。
2. 語域（顧客向け）: 二重敬語（おっしゃられる、拝見させていただく）、「ご〜させていただきます」の乱用、「〜になります」「〜のほう」、クッション言葉の連打、「〜かと存じます」「〜と思われます」で確信度を均している箇所、文書での「御社」、結びの定型の重複、添付がないのに「ご査収ください」。
3. 字形・記号: 全角英数、半角句読点の混入、「，」「；」「“”」、簡体字など JIS にない字、範囲記号の不統一（〜／～／-）、丸数字と括弧数字の混在、太字の密度。
4. 問題のある箇所だけを次の形式で列挙する。
   - 原句:
   - 類型: 翻訳調/語域/字形
   - 判定: REWRITE / HOLD
   - 指令: どの形に戻すか（規則名または表層目録の項目）。文案は書かない。
5. 末尾に Lane C の総合判定を PASS / WARN / FAIL で書く。FAIL は顧客向け文書に敬語の誤りまたは字形の混入が1件でもある場合。
```

## quick モードの統合プロンプト

サブエージェント1体に、上の3つのプロンプトを「Lane A」「Lane B」「Lane C」の節見出し付きで連結して渡す。Lane A の機能表は省略可（quick では列挙だけでよい）。出力の末尾に3つの総合判定を並べさせる。

## 親の統合手順

1. Lane 0（機械検出）の findings と Lane A/B/C の所見を一つの台帳にする。形式は natural-japanese の判断台帳と同じ。

```
- [直した] LaneB/証拠越境: 「全リージョンで利用可能」→ 確認済みの3リージョンに限定し、他は【要確認】
- [直した] LaneA/審査式話語: 「上記は公式ドキュメントで確認済み」を削除し、該当URLを参考リンクへ
- [残す/体裁上自然] Lane0/bullet_dominant: customer-qa-style の箇条書き型なので対象外
- [残す/技術用語] LaneC/翻訳調「することができる」: API仕様の可能表現として正確さを優先
- [HOLD→ユーザー確認] LaneB/HOLD: 圧縮率の実測値がないため幅を書けない。実測を依頼
```

2. 「直した」は SKILL.md の固定操作表だけで行う。自由な潤色はしない。前提・適用範囲・未検証項目は削らない。
3. 「残す」には理由の種類を必ず添える（体裁上自然・技術用語・固有名詞・文脈上必要・ジャンル上自然）。理由なしの「残す」は判断放棄。
4. 修正後、Lane 0 を再実行する（`--baseline` に前回の JSON を渡すと resolved/new/persisting に仕分けられる）。
5. 第2ラウンドは、変更した文と、その前後1文だけを新しいサブエージェントに渡す。全文を再レビューしない（全文を渡すと第1ラウンドで KEEP だった文に別の指摘が付き、収束しない）。
6. 終了条件: 第2ラウンドで新規 finding がない、または残る finding がすべて「残す（理由）」か「HOLD→ユーザー確認」に仕分けられている。
7. 発散ガード: 同じ文に同じ類型の finding が2ラウンド連続で付いたら、規則でなく素材の不足（証拠・数値・一次情報がない）である。文を直し続けず、何を確認すれば書けるかをユーザーに返す。

## 判定の例

**例1 過度防御（顧客回答）**
- 原句: 「本構成でも概ね問題ないかと存じますが、環境によっては想定通りに動作しない可能性もございます。」
- 類型: 過度防御 ／ 判定: REWRITE
- 指令: 「概ね」「環境によっては」が指す条件を特定する。確認済みの構成（リージョン・エディション・同時実行数）を結果として書き、未検証の条件を列挙し、どちらでもない「可能性」は削る。

**例2 審査式話語（分析レポート）**
- 原句: 「上記の内容は複数回の検証を経ており、全項目のチェックを通過しているため、本資料の結論は信頼できます。」
- 類型: 審査式話語 ／ 判定: DELETE
- 指令: 削除。信頼の根拠を残したいなら、どの数値がどの一次データから得られ、どの範囲でだけ成り立つかを、対象についての文として書く。

**例3 証拠越境（提案書）**
- 原句: 「本方式はデータ遅延の問題を全面的に解決でき、他の業務システムにもそのまま適用可能です。」
- 類型: 証拠越境 ／ 判定: REWRITE
- 指令: 「全面的に」「そのまま適用可能」に対応する証拠が本文にない。実測した業務システム・データ量・遅延の改善幅を結果として書き、未検証の系統（他業務・他規模）を明記する。

**例4 過度説明（技術解説）**
- 原句: 「まず第一の不等式で上から抑え、次に第二の不等式で交差項を処理し、その後三つの関数をそれぞれ評価して代入することで最終的な上界が得られ、この上界は多数のサンプル点での数値検証によってもその妥当性が確認されており、手法の頑健性を示している。」
- 類型: 過度説明 ／ 判定: REWRITE
- 指令: 結果（複合不等式から得られる上界）を一文にする。数値検証は「上界と実装の一致を確認する目的で行った」と役割だけ書き、「頑健性」は検証した範囲が本文にない限り削る。証明の手順は付録か参照先へ。

**例5 語域（顧客メール）**
- 原句: 「ご提案させていただきました内容について、ご確認させていただければと存じますので、お手数ですがご回答のほうをよろしくお願いいたします。」
- 類型: 語域 ／ 判定: REWRITE
- 指令: 「ご提案させていただきました」→提案した、「ご確認させていただければ」→ご確認ください、「ご回答のほう」→ご回答、クッション言葉は一通に1回。依頼の期限があるなら添える。
